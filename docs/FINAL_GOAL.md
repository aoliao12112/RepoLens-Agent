# RepoLens Agent 最终目标

## 最终产品

用户输入一个 GitHub 仓库地址和自己的使用目标，例如“判断该项目是否适合作为 Agent 开发实习的二次开发项目”。系统自动采集仓库公开信息，调度不同角色完成专项审查，通过证据校验后输出一份结构化技术尽调报告。

报告必须回答：项目在做什么、是否仍在维护、代码是否具备工程基础、主要依赖与运行门槛、许可证是否允许二次开发、有哪些显著风险、与用户目标的匹配程度，以及建议继续使用还是放弃。

## 核心工作流

1. 输入校验：解析 GitHub URL，拒绝非 GitHub 地址和无效仓库。
2. 数据采集：调用 GitHub API 获取仓库元数据、语言、README、许可证、目录树、近期提交和 Issue 信息。
3. 任务规划：规划 Agent 根据用户目标决定需要执行哪些审查，不固定堆叠所有步骤。
4. 并行审查：维护审查、工程审查、许可证审查和目标适配审查并行执行。
5. 证据校验：验证报告中的关键结论是否能追溯到 API 字段、仓库文件或网页链接。
6. 风险汇总：合并重复问题，区分事实、推断和待人工确认项。
7. 人工确认：用户确认分析目标与关键风险后再导出最终报告。

## 必须实现的工具

- `get_repository_metadata`：Stars、Forks、创建时间、更新时间、默认分支和归档状态。
- `get_languages_and_tree`：主要语言、关键目录、配置文件和测试目录。
- `get_readme_and_license`：README、许可证类型和归属说明。
- `get_recent_activity`：近期提交频率、贡献者分布和发布记录。
- `get_issue_signals`：Open Issue 数量、长期未处理问题和常见故障主题。
- `evaluate_target_fit`：根据用户目标生成明确的匹配项与缺口。
- `verify_evidence`：检查每条高风险判断是否具有来源。

## 工程目标

- Python 3.11 及以上。
- 使用异步 HTTP 客户端并限制并发数。
- 对 GitHub API 限流、超时和临时失败实现重试与明确错误提示。
- 使用 SQLite 缓存短期重复请求，并记录分析任务状态。
- 使用 Pydantic 定义工具输入、工具输出和最终报告结构。
- 提供 FastAPI 接口和一个简单 Web 演示页面。
- 使用结构化日志记录每次工具调用的耗时、状态和错误类型。
- 支持在没有模型 API Key 时运行基础数据采集与规则评分。

## 最终报告结构

- 仓库概况。
- 维护活跃度。
- 工程质量与可运行性。
- 许可证和依赖风险。
- 与用户目标的匹配分析。
- 高风险问题及证据。
- 采用建议：推荐、谨慎采用或不推荐。
- 一周二次开发建议。

## 评测要求

- 选择不少于 20 个公开仓库，覆盖活跃、低维护和已归档项目。
- 人工标注归档状态、许可证、主要语言、是否存在测试和最近更新时间。
- 统计字段抽取正确率、结构化输出成功率、证据覆盖率、平均耗时和单次模型费用。
- 对至少 5 个仓库进行人工复核，记录 Agent 判断错误及修正原因。
- 所有简历指标来自保存的评测结果，禁止估算或编造。

## 完成标准

- 输入一个真实 GitHub URL，可以稳定生成完整报告。
- 每项关键事实均能定位到 GitHub API 字段、仓库文件或网页链接。
- 单个工具失败不会让整个任务无提示崩溃。
- 核心逻辑有单元测试，完整流程有端到端测试。
- README 包含安装、运行、架构、评测结果、已知限制和演示截图。
- Git 历史能显示个人逐步实现过程，不能只有一次大提交。
- 有 60 至 90 秒演示视频，并能现场解释一次错误判断的排查过程。

达到以上条件后，该项目可以替换简历中的大学数据库课设。项目名称建议使用“GitHub 开源项目技术尽调 Agent”。
