# RepoLens Agent 项目深挖与面试表达

## 一、项目一句话介绍

RepoLens Agent 是一个面向公开 GitHub 仓库的技术尽调系统。用户输入仓库地址和实际使用目标后，系统自动采集仓库事实，从维护活跃度、工程质量、许可证风险和目标适配度四个维度进行分析，最终生成带证据链接、可人工确认、可导出的结构化报告。

这个项目解决的不是“让模型介绍一个仓库”，而是“在学习、选型或二次开发之前，如何用可复核的公开证据判断一个仓库是否值得投入”。

## 二、我在项目中主要做了什么

### 1. 从零设计并实现完整的 Agent 应用闭环

我负责将最初只有 URL 解析和少量数据模型的代码骨架，扩展成可以实际运行的完整系统，打通了以下流程：

```text
用户输入 GitHub URL 和目标
    → 创建异步分析任务
    → 并发采集 GitHub 数据
    → 规则审查和可选模型审查
    → 证据校验与风险归并
    → 生成人工确认前的报告
    → 确认风险
    → 导出 JSON / Markdown
```

系统不是一次 HTTP 请求里同步完成所有工作，而是使用任务状态机管理 `queued`、`collecting`、`reviewing`、`verifying`、`awaiting_confirmation`、`completed` 和 `failed` 等阶段，让前端能够持续展示真实进度和失败原因。

### 2. 建立可靠的 GitHub 数据采集层

我使用 HTTPX 实现异步 GitHub API 客户端，采集：

1. 仓库元数据：Star、Fork、默认分支、归档状态、更新时间等；
2. 语言和目录树：主要语言、依赖文件、测试、CI、Docker、文档、示例和入口文件；
3. README 与许可证：README 正文、许可证类型、路径和识别状态；
4. 近期活动：提交、贡献者集中度和 Release；
5. Issue 信号：Open Issue、Pull Request、长期未处理问题、响应时间和常见问题主题。

客户端集中处理超时、连接失败、GitHub 限流、可恢复的 `5xx`、重试退避、请求并发上限和错误转换。请求结果通过 SQLite TTL 缓存复用，降低重复请求和 GitHub 配额消耗。

### 3. 实现无模型也能工作的确定性分析基线

我没有把整个项目做成“必须调用大模型才能运行”的包装层，而是先实现了确定性规则分析器：

- 维护度：归档状态、最近提交、提交频率、Release、Issue 积压和贡献者集中度；
- 工程质量：依赖声明、测试、CI、Docker、文档、示例和入口结构；
- 许可证：明确许可证、缺失许可证、无法识别的许可证文件和待人工复核状态；
- 目标适配：从用户目标中提取 Python、Agent、API、Web、Docker、测试和 CI 等条件，与仓库信号匹配。

每条规则都保留规则 ID、分数变化、解释和证据，因此相同输入可以得到稳定、可回归测试的结果。即使没有模型 Key，系统仍能完成采集、评分、证据校验、确认和导出。

### 4. 实现 Agent 规划、并行专项审查和自动降级

在规则基线之上，我使用 OpenAI Agents SDK 设计了目标驱动的审查编排：

1. 规划器根据用户目标生成审查计划和优先级；
2. 维护、工程、许可证、目标适配四个专项审查可受控并发执行；
3. 模型输出由 Pydantic 结构约束；
4. 模型只能引用输入中存在的证据 ID，不能自行生成来源；
5. 单个专项审查超时、报错或输出非法时，只降级该章节，不拖垮整份报告；
6. 没有模型 Key 时自动进入规则模式。

模型在这里负责解释和归纳，仓库事实仍以 GitHub 采集结果为准。这样既保留 Agent 的动态分析能力，也避免模型成为单点故障。

### 5. 建立证据约束和人工确认机制

我实现了独立的证据校验器，用于检查：

- 证据 ID 是否真实存在；
- 链接是否属于目标 GitHub 仓库或 GitHub API；
- 文件路径或 API 字段是否可定位；
- 高风险结论是否至少有一条直接证据；
- 重复风险是否应该合并。

系统明确区分 `fact`、`inference` 和 `needs_confirmation`。无证据的高风险结论不能伪装成已验证事实，而是降级为待确认。报告在用户确认目标与风险之前保持草稿状态，确认记录写入 SQLite，形成可审计闭环。

### 6. 完成 API、Web 页面和可复现评测

我使用 FastAPI 提供创建任务、查询进度、获取报告、确认报告和健康检查接口，并使用原生 HTML、CSS、JavaScript 实现轻量 Web 页面。页面支持：

- 仓库和目标输入；
- 规则/模型模式选择；
- 任务进度和可重试错误；
- 四个审查章节和风险标签；
- 逐条证据链接；
- 人工确认；
- JSON 和 Markdown 导出；
- 移动端基础适配。

此外，我实现了批量评测命令，逐仓库保存状态、快照、报告、耗时和错误，并从真实产物自动计算指标，避免在 README 中手填无法复现的数据。

## 五、项目中的关键难点及解决方法

### 难点 1：GitHub API 不稳定，部分失败不能拖垮整份报告

**问题**：GitHub API 可能出现限流、超时、连接错误、临时 `5xx`、分页截断或单个接口失败。如果简单使用 `asyncio.gather`，一个请求异常就可能导致整个任务失败；如果直接把回退值 `0` 当成事实，又会产生错误结论。

**解决**：

1. 建立统一请求层，只重试连接错误、超时、`429` 和可恢复 `5xx`；
2. 使用指数退避、`Retry-After`、限流重置时间和并发信号量；
3. 各采集工具独立记录 `success`、`partial` 或 `failed`；
4. 单工具失败时返回结构化占位结果，但规则层读取 `collection_status`；
5. 采集失败产生的是“数据不可用、待确认”，不是“提交数为零”等伪事实。

**效果**：系统能够保留成功章节并明确标记降级。真实烟雾评测曾发现“近期活动采集失败后，零值被当成事实”的问题，修复后同一案例从报告生成失败变为成功生成待确认报告。

### 难点 2：仓库改名和重定向导致数据与证据身份不一致

**问题**：`facebook/react` 已重定向到规范仓库名 `react/react`。早期客户端没有跟随 GitHub `301`，将重定向响应误当成仓库元数据，导致字段缺失；即使只修 HTTP 重定向，后续证据仍可能使用旧仓库名，与报告中的规范仓库名不一致。

**解决**：

1. HTTP 请求显式跟随安全重定向；
2. 元数据返回后解析 GitHub 的规范 `full_name`；
3. 后续语言、目录、README、许可证、活动和 Issue 采集全部切换到规范仓库引用；
4. 增加仓库重命名回归测试。

**效果**：第一轮 20 仓评测为 18 成功、2 失败；修复重定向并替换已不可访问的评测样本后，第二轮达到 20/20 成功。

### 难点 3：如何控制模型幻觉，让结论可以复核

**问题**：如果让模型自由阅读摘要并生成报告，它可能补充不存在的文件、链接或风险原因。文字看起来合理，但无法用于技术选型。

**解决**：

1. 采集事实与模型结论分层保存；
2. 给每条事实分配稳定证据 ID；
3. 模型输出只允许引用输入证据 ID；
4. 使用 Pydantic 校验结构、评分和枚举；
5. 最终报告前再次校验证据域名、仓库归属、字段和路径；
6. 无证据的高风险项强制降级为待确认。

**效果**：报告可以从结论追溯到 GitHub API 字段、仓库文件或页面链接。20 仓规则评测中，非待确认结论的证据覆盖率达到 100%。

### 难点 4：模型可能不可用、昂贵或输出格式不稳定

**问题**：如果模型 Key 缺失、余额不足、接口超时或 JSON 输出不合法，纯模型应用会直接失效，而且难以做稳定测试。

**解决**：

1. 先建立无模型的规则基线；
2. 模型只做增强，不覆盖采集事实；
3. 四个专项审查隔离并受控并发；
4. 单章节失败时回退到对应规则结果；
5. 真实 Token 用量和费用只有在上游返回时才记录，不估算；
6. 空 Key 统一归一化为未配置，避免生成非法认证请求头。

**效果**：没有任何模型 Key 时，系统仍可完成完整分析闭环；模型异常不会让核心产品不可用。空 `GITHUB_TOKEN=` 曾导致非法 `Bearer` 请求头，修复并补充回归测试后，真实仓库分析恢复正常。

### 难点 5：异步任务状态、缓存和服务重启的一致性

**问题**：分析过程包含多次网络调用，无法要求用户一直等待一个同步请求。若只把状态放在内存中，服务重启后任务和报告会丢失或被错误标记为成功。

**解决**：

1. 使用 SQLite 保存请求、阶段、进度、错误、报告和确认记录；
2. 通过任务状态迁移规则阻止非法跳转；
3. 后台错误统一转换为稳定错误码、用户消息和 `retryable` 标记；
4. 服务启动时识别遗留未完成任务并明确标记失败；
5. 缓存使用 TTL、数据版本和并发写保护，损坏缓存不阻断主流程。

**效果**：前端能够展示真实阶段，失败后不会永久加载；服务重启不会把中断任务伪装成已完成。

### 难点 6：评测指标容易被写得漂亮但不可复现

**问题**：Agent 项目常见问题是展示几个成功截图，就声称高准确率；但没有数据集、标注、失败记录和指标计算代码。

**解决**：

1. 建立 20 仓评测清单和严格标注结构；
2. 每个案例独立保存成功或失败结果；
3. 指标从保存产物自动计算；
4. 未人工标注时 `field_accuracy` 必须为 `null`；
5. 未得到真实费用时平均费用必须为 `null`；
6. 保留 v1 失败原因和 v2 修复结果。

**效果**：项目目前可以诚实证明“20/20 生成报告”和“证据覆盖率 100%”，但不会虚构准确率。这种评测可信度比一个未经验证的高数字更有价值。

## 七、面试时建议如何讲

建议按以下顺序，而不是上来罗列技术名词：

1. **先讲问题**：Star 数不能回答项目是否活跃、能否二次开发、许可证是否明确以及是否适合具体目标。
2. **再讲设计**：事实采集、规则基线、模型增强、证据质量闸门和人工确认五层分离。
3. **重点讲难点**：部分 API 失败不能产生伪事实；模型不能生成不存在的证据；仓库重命名导致身份漂移。
4. **给真实结果**：99 项测试、20/20 报告生成、100% 证据覆盖、约 10.11 秒平均耗时。
5. **主动讲边界**：没有人工标注，所以不宣称准确率；许可证结果不是法律意见；首版只支持公开 GitHub 仓库。
6. **最后讲下一步**：完成人工标注，增加 DeepSeek 等低成本兼容模型，对规则与模型模式分别测量准确率、费用和延迟。

这种表达能体现你不只是“调用了一个大模型 API”，而是完成了 Agent 系统中的工具可靠性、结构化输出、证据约束、故障降级、状态持久化和可复现评测。
