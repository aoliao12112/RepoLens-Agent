# RepoLens Agent 详细修改目标与实施批次

本文将 `FINAL_GOAL.md` 中的产品目标拆成可开发、可测试、可提交、可验收的实施批次。批次按依赖顺序排列；每批完成后都应保持主分支可运行，不接受“代码先堆上去，最后统一补测试”的做法。

## 1. 总体修改目标

将当前仅具备 GitHub URL 解析、基础仓库元数据模型和单接口客户端的工程骨架，升级为一个可稳定运行的 GitHub 开源项目技术尽调系统：用户提交公开 GitHub 仓库地址和使用目标后，系统能够采集仓库事实、按目标规划审查任务、并行完成专项分析、验证高风险结论的证据，并通过 API 和 Web 页面输出结构化报告。

最终实现必须同时满足以下要求：

1. **事实完整**：覆盖仓库概况、语言与目录、README、许可证、提交、贡献者、Release 和 Issue 信号。
2. **结论可追溯**：报告中的关键事实和高风险判断必须关联 API 字段、仓库文件或网页链接。
3. **运行可靠**：正确处理无效 URL、仓库不存在、权限不足、限流、超时、临时网络错误和部分工具失败。
4. **按目标分析**：审查流程由用户目标驱动，能够明确给出匹配项、缺口和采用建议，而不是固定拼接通用结论。
5. **无模型可用**：没有模型 API Key 时，基础采集、规则评分和报告骨架仍可运行。
6. **工程可交付**：具备缓存、任务状态、结构化日志、单元测试、端到端测试、评测结果、使用文档和演示材料。

## 2. 当前基线与主要缺口

### 已有能力

- `github_url.py` 可解析常见 GitHub 仓库 URL。
- `github_client.py` 可获取单个仓库的基础元数据。
- `models.py` 已有仓库、证据、建议和报告的初始 Pydantic 模型。
- 已配置 Python 3.11、FastAPI、HTTPX、SQLite、Agents SDK、pytest 和 Ruff 依赖。

### 当前缺口

- URL 解析规则仍较宽松，尚未覆盖非法路径、查询参数、大小写及边界字符。
- GitHub 客户端没有统一异常、重试、限流提示、并发控制和响应缓存。
- 尚未实现语言、目录树、README、许可证、提交、贡献者、Release 和 Issue 采集。
- 当前报告模型不足以表达审查章节、评分、事实/推断/待确认分类及逐条证据。
- 尚无规则分析器、Agent 规划器、并行审查、证据校验与降级路径。
- 尚无 FastAPI 任务接口、任务状态持久化、Web 页面和人工确认流程。
- 评测仓库清单为空，缺少批量评测、指标计算和失败案例记录。
- 测试仅覆盖 URL 解析，尚无客户端、分析器、服务层和端到端测试。

## 3. 实施原则

- 每个批次只引入一组清晰能力，并附带对应测试、文档和错误处理。
- GitHub 原始事实与分析结论分层保存，避免模型输出污染事实数据。
- 所有外部响应先转换为 Pydantic 模型，再进入分析和报告流程。
- 规则分析是稳定基线；模型分析只能增强结果，不能成为系统可运行的前提。
- 高风险结论无有效证据时不得进入最终建议，应降级为“待人工确认”。
- 并发必须有上限；重试仅用于超时、连接错误、`429` 和可恢复的 `5xx`。
- 测试不得依赖真实 GitHub 网络状态，客户端单测使用 MockTransport 或等价替身。
- 每批建议形成 1 至 3 个语义明确的小提交，禁止最终一次性提交全部功能。

## 4. 分批实施计划

### 批次 0：固定领域模型与错误契约

**状态**：已完成（2026-10-26）。

**目标**：先稳定全系统的数据边界，避免后续采集、分析和 API 各自定义一套结构。

**修改内容**：

- 扩展 `models.py`，增加以下模型：
  - `AnalysisRequest`：仓库 URL、用户目标、是否启用模型分析。
  - `RepositorySnapshot`：元数据、语言、目录信号、README、许可证、活动和 Issue 信号。
  - `ReviewFinding`：标题、说明、严重程度、结论类型、证据列表、待确认标记。
  - `ReviewSection`：维护、工程、许可证、目标适配四类章节及其评分。
  - `AnalysisTask`：任务 ID、状态、进度、错误摘要、创建和更新时间。
  - 完整版 `DueDiligenceReport`：概况、各审查章节、风险、建议和一周计划。
- 增加枚举：任务状态、风险等级、结论类型、审查类型和工具状态。
- 新建统一异常层，至少区分输入错误、仓库不可访问、GitHub 限流、上游超时、上游临时失败和内部分析错误。
- 明确所有时间使用带时区的 UTC `datetime`，所有评分范围统一为 `0-100`。
- 为模型序列化、字段约束、枚举值和异常映射补充单元测试。

**交付物**：领域模型、异常模块、模型测试、示例 JSON。

**验收标准**：

- 合法的完整报告可以通过 Pydantic 校验并稳定序列化为 JSON。
- 缺失必填字段、非法评分、无来源的事实结论会在模型层或业务层被拒绝。
- 后续批次无需再创建平行的请求、任务或报告数据结构。

**依赖**：无。

### 批次 1：强化输入校验与 GitHub 客户端基础设施

**状态**：已完成（2026-10-26）。

**目标**：建立可被所有采集工具复用的可靠 HTTP 访问层。

**修改内容**：

- 收紧 GitHub URL 解析：仅接受仓库根路径或明确允许的子路径，拒绝空名称、非法字符和非 GitHub 主机伪装。
- 为客户端注入 `httpx.AsyncClient`，便于测试和复用连接池。
- 增加统一请求方法，集中处理认证头、超时、状态码、JSON 解析和异常转换。
- 对连接错误、超时、`429`、`502`、`503`、`504` 实现有限次数指数退避；不重试 `400`、`401`、`403`、`404` 等确定性错误，但单独识别限流型 `403`。
- 读取 `X-RateLimit-Remaining`、`X-RateLimit-Reset` 和 `Retry-After`，生成明确限流信息。
- 使用 `asyncio.Semaphore` 限制 GitHub 请求并发数，并通过配置项控制超时、重试次数和并发上限。
- 记录请求工具名、耗时、状态、重试次数和错误类型；严禁记录 Token 和完整请求头。

**交付物**：可靠 GitHub 请求层、配置模型、异常映射测试、重试与并发测试。

**验收标准**：

- 404、限流、超时和可恢复 5xx 均返回可识别的领域错误。
- 测试能证明可恢复错误按配置重试，确定性错误不会重试。
- 并发请求数不会超过配置上限。
- 日志中不出现认证 Token。

**依赖**：批次 0。

### 批次 2：完成六类 GitHub 数据采集工具

**状态**：已完成（2026-10-26）。

**目标**：实现最终目标要求的完整、结构化、可独立调用的数据采集层。

**修改内容**：

- 完善 `get_repository_metadata`：基础计数、默认分支、归档状态、时间和仓库链接。
- 实现 `get_languages_and_tree`：
  - 获取语言占比与递归目录树。
  - 识别依赖文件、测试目录、Docker、CI、文档、示例和入口文件。
  - 处理超大目录树被 GitHub 截断的情况，并保留“不完整”标记。
- 实现 `get_readme_and_license`：
  - 获取 README 文本、路径和网页链接。
  - 获取许可证 SPDX、许可证文件路径和归属说明。
  - 区分“无许可证”“未知许可证”和“API 未识别但存在许可证文件”。
- 实现 `get_recent_activity`：
  - 获取指定观察窗口内的提交、贡献者和 Release。
  - 计算最近提交时间、月均提交、贡献者集中度和最近 Release 时间。
- 实现 `get_issue_signals`：
  - 获取 Open Issue 数、Issue/PR 区分、长期未处理数量和响应时间样本。
  - 用可解释的关键词规则汇总常见故障主题，并保留样本链接。
- 为每个工具输出标准化证据对象，保留 API URL、网页 URL 或文件路径。

**交付物**：六类采集工具、响应模型、Mock 单元测试、采集快照示例。

**验收标准**：

- 每个工具既可单独调用，也可合并为 `RepositorySnapshot`。
- API 字段缺失、空仓库、无 Release、无 Issue、超大目录树均能正常返回，不因 `KeyError` 崩溃。
- 每项核心事实至少关联一个可定位的证据来源。
- 工具测试覆盖成功、空数据、字段缺失和上游错误场景。

**依赖**：批次 1。

### 批次 3：SQLite 缓存、任务状态与结构化日志

**状态**：已完成（2026-10-26）。

**目标**：减少重复 API 消耗，并为异步分析任务提供可恢复、可观察的状态基础。

**修改内容**：

- 建立 SQLite 初始化与轻量迁移机制。
- 增加缓存表：请求键、响应 JSON、创建时间、过期时间和数据版本。
- 按数据类型设置 TTL；仓库静态信息与近期活动采用不同有效期。
- 增加任务表：任务状态、进度、当前阶段、错误摘要、请求参数、报告位置和时间戳。
- 实现缓存命中、过期刷新、损坏数据淘汰和并发写入保护。
- 使用 JSON 结构化日志输出 `task_id`、`tool`、`duration_ms`、`status`、`error_type` 和 `cache_hit`。
- 对用户目标等文本做长度限制；日志不写入 Token、请求头和不必要的用户原文。

**交付物**：数据库模块、缓存仓储、任务仓储、日志配置和测试。

**验收标准**：

- 相同请求在 TTL 内不会重复访问 GitHub API。
- 过期或损坏缓存可安全刷新，不影响主流程。
- 任务状态可从 `queued` 依次流转到 `collecting/reviewing/verifying/completed`，失败时保存可读错误。
- 并发任务不会因 SQLite 锁冲突频繁失败。

**依赖**：批次 0；接入采集层时依赖批次 2。

### 批次 4：规则分析与无模型降级报告

**状态**：已完成（2026-10-26）。

**目标**：在没有模型 API Key 的情况下，也能基于事实生成可解释的基础尽调结果。

**修改内容**：

- 实现维护度规则：归档状态、最近提交、提交频率、Release、新旧 Issue 和贡献者集中度。
- 实现工程质量规则：依赖文件、测试、CI、Docker、文档、示例、主要语言和目录完整度。
- 实现许可证规则：许可证是否存在、SPDX 是否明确、二次开发提示和人工复核条件。
- 实现目标适配规则：从用户目标中提取技术栈、用途和限制关键词，与仓库事实进行匹配。
- 为每条规则记录规则 ID、输入事实、得分变化、解释和证据。
- 定义评分权重和推荐阈值；任何硬性风险可覆盖总分，不能用平均分掩盖“已归档”或“无明确许可证”等问题。
- 生成基础报告和一周二次开发建议，并明确标记规则推断的局限。

**交付物**：四类规则审查器、评分器、基础报告生成器、规则测试。

**验收标准**：

- 未配置模型 Key 时，输入采集快照和用户目标仍能输出完整报告结构。
- 相同输入产生确定性结果。
- 每项扣分和高风险判断可追溯到规则与证据。
- 已归档、无许可证、无测试、近期活跃等典型夹具得到符合预期的不同建议。

**依赖**：批次 0、2。

---

### 批次 5：Agent 规划、并行专项审查与模型降级

**状态**：已完成（2026-10-26）。

**目标**：加入由用户目标驱动的动态审查流程，同时确保模型不可用时自动回落到规则结果。

**修改内容**：

- 实现规划器：根据目标选择维护、工程、许可证和适配审查，并生成选择理由。
- 将四类审查封装为边界明确的审查任务，输入仅包含所需快照切片，输出统一为 `ReviewSection`。
- 使用受控并发执行互不依赖的审查，单个审查失败时保留其他结果并标记降级。
- 使用 Pydantic 约束模型输出；解析失败时最多进行有限修复，之后使用规则审查结果。
- 模型只能引用提供给它的证据 ID，不允许自行生成不存在的 URL、文件或统计数据。
- 合并规则与模型结果：事实以采集层为准，模型用于解释、归纳和目标匹配，不覆盖已验证事实。
- 记录模型名称、调用耗时、Token 用量和估算费用；未获得真实返回值时不得编造费用。

**交付物**：规划器、四类审查 Agent、并行编排器、模型适配器、降级测试。

**验收标准**：

- 不同用户目标能够产生不同审查计划或不同关注权重。
- 一个 Agent 超时或输出非法结构时，完整任务仍能返回带降级说明的报告。
- 没有模型 Key 时自动使用批次 4 的规则报告，不产生启动错误。
- 模型输出无法引用输入证据集合之外的来源。

**依赖**：批次 4。

### 批次 6：证据校验、风险归并与人工确认

**状态**：已完成（2026-10-26）。

**目标**：形成最终报告前的质量闸门，系统性降低无来源结论和重复风险。

**修改内容**：

- 实现 `verify_evidence`：检查证据 ID 是否存在、来源类型是否合法、字段或路径是否可定位、链接是否属于目标仓库或 GitHub API。
- 对高风险判断执行强校验：至少一条直接证据；只有间接证据时降级为推断；无证据时移入待确认。
- 按规则 ID、证据和语义键合并重复风险，保留最高严重程度和全部有效来源。
- 明确区分 `fact`、`inference`、`needs_confirmation`，并在最终报告中可见。
- 增加人工确认状态：用户可确认目标、接受风险或要求重新分析；未确认前报告处于草稿状态。
- 固化最终建议生成规则，防止报告正文与推荐等级互相矛盾。

**交付物**：证据校验器、风险归并器、确认服务和测试。

**验收标准**：

- 无证据的高风险结论无法进入已验证风险列表。
- 重复风险被合并且不丢失来源。
- 篡改的证据 ID、跨仓库链接和不存在的路径会被识别。
- 用户确认前后报告状态清晰可辨，并保留确认记录。

**依赖**：批次 5。

### 批次 7：FastAPI 服务与任务接口

**状态**：已完成（2026-10-26）。

**目标**：通过稳定 API 暴露完整分析流程，为 Web 演示和自动化评测提供入口。

**修改内容**：

- 新建 FastAPI 应用、生命周期管理和依赖注入。
- 至少提供以下接口：
  - `POST /api/analyses`：创建分析任务。
  - `GET /api/analyses/{task_id}`：查询状态和进度。
  - `GET /api/analyses/{task_id}/report`：获取草稿或最终报告。
  - `POST /api/analyses/{task_id}/confirm`：确认目标与风险。
  - `GET /health`：健康检查。
- 使用后台任务或应用内任务队列执行分析；进程重启后对未完成任务给出明确状态，不伪装为成功。
- 定义稳定的 HTTP 错误响应：错误码、用户消息、是否可重试和请求追踪 ID。
- 增加请求大小、目标文本长度、CORS 和基础安全配置。
- 编写 API 集成测试，外部 GitHub 与模型调用全部替换为测试替身。

**交付物**：FastAPI 应用、服务层、路由、API Schema 和集成测试。

**验收标准**：

- 能通过 API 完成“创建任务—查询进度—获取报告—人工确认”闭环。
- 非法输入返回 4xx，上游临时失败返回可重试信息，内部错误不泄露堆栈和密钥。
- 两个并发任务的数据、日志和报告不会串线。

**依赖**：批次 3、6。

### 批次 8：Web 演示页与报告导出

**状态**：已完成（2026-10-26）。

**目标**：提供足够完成演示和人工复核的轻量界面，不把精力浪费在复杂前端框架上。

**修改内容**：

- 增加单页 Web 界面：仓库 URL、用户目标和模型开关输入。
- 展示任务阶段、进度、可重试错误和缓存命中信息。
- 报告按概况、维护、工程、许可证、目标适配、风险、建议和一周计划分区展示。
- 每项高风险判断可展开查看证据类型、字段/路径和链接。
- 对事实、推断、待确认使用明确标签，而不是只靠颜色区分。
- 实现目标与风险确认操作；确认后允许导出 Markdown 和 JSON。
- 加入加载、空数据、失败、部分降级和移动端基本布局。

**交付物**：静态 Web 页面、交互脚本、样式、导出功能和页面测试/人工检查清单。

**验收标准**：

- 新用户无需阅读源码即可提交任务并理解结果。
- API 错误和部分工具失败在页面上有明确说明，不出现永久加载。
- 证据链接可点击且对应正确仓库、文件或 API 来源。
- 导出的 JSON 可再次通过报告模型校验，Markdown 包含全部必要章节。

**依赖**：批次 7。

### 批次 9：评测体系、质量收口与最终交付

**状态**：进行中（2026-10-26）。已完成 20 仓规则模式运行、指标计算、失败回归、架构与演示文档；仍需人工标注与至少 5 仓人工复核。

**目标**：用真实保存的结果证明系统质量，并补齐简历项目所需的交付材料。

**修改内容**：

- 在 `data/evaluation/repositories.json` 中选择不少于 20 个公开仓库，覆盖活跃、低维护、已归档、不同语言和许可证情况。
- 人工标注归档状态、许可证、主要语言、测试存在性和最近更新时间；标注应保存来源和标注时间。
- 实现批量评测命令，保存每个仓库的原始输出、预测结果、耗时、Token 和费用。
- 计算字段抽取正确率、结构化输出成功率、证据覆盖率、平均耗时和真实平均费用。
- 至少人工复核 5 个仓库，记录错误结论、根因、修复和修复后结果。
- 增加完整流程端到端测试、关键分支覆盖、Ruff 检查和密钥扫描。
- 完善 README：安装、配置、运行、架构、API、无模型模式、评测结果、已知限制、截图和演示说明。
- 绘制架构图，准备 60 至 90 秒演示视频脚本，并核查 Git 历史能体现逐步实现过程。

**交付物**：评测数据集、批量评测脚本、指标报告、失败案例文档、完整 README、架构图和演示材料。

**验收标准**：

- 20 个仓库可批量执行并保存可复现结果，失败项有原因而非静默丢失。
- README 中的所有数值均能从保存的评测产物重新计算，禁止估算或美化。
- 至少 5 个失败案例具有明确的人工复核记录。
- 全部单元测试、集成测试、端到端测试和静态检查通过。
- 使用一个真实 GitHub URL 能稳定生成完整、带证据、可确认和可导出的报告。

**依赖**：批次 8。

## 5. 批次依赖与建议提交节奏

```text
批次 0 领域模型与异常
  ├─> 批次 1 HTTP 基础设施 ─> 批次 2 数据采集 ─┐
  └─> 批次 3 缓存与任务状态 <──────────────────┤
                                                  v
批次 4 规则分析 ─> 批次 5 Agent 编排 ─> 批次 6 证据校验
                                                  |
                                                  v
批次 7 API ─> 批次 8 Web ─> 批次 9 评测与交付
```

建议每批遵循以下提交顺序：

1. 先提交数据结构或接口契约及其测试。
2. 再提交实现与异常处理。
3. 最后提交集成测试和文档更新。

提交信息示例：

- `feat(models): define repository snapshot and review findings`
- `feat(github): add retry and rate-limit handling`
- `test(analysis): cover archived and unlicensed repositories`
- `docs: record evaluation results and known limitations`

## 6. 每批统一完成定义

一个批次只有同时满足下列条件才能标记完成：

- 计划内功能已实现，没有用空函数、硬编码成功结果或未说明的 TODO 代替。
- 新增行为有成功、边界和失败路径测试。
- `pytest` 全部通过，Ruff 不新增告警。
- 错误信息对用户可理解，日志对开发者可定位，且两者都不泄露密钥。
- Pydantic 模型、API Schema、实现和文档保持一致。
- 新增配置已写入示例环境变量文件或 README，默认值安全可运行。
- 本批产生的真实限制已记录，不通过夸大描述掩盖。
- Git 提交粒度清晰，可单独回顾本批引入的能力。

## 7. 明确不在首版范围内的内容

为确保首版按时交付，以下功能暂不纳入上述批次：

- 私有 GitHub 仓库、GitLab、Gitee 等其他代码托管平台。
- 克隆仓库后执行不受信任代码、构建项目或运行第三方测试。
- 企业级账户、权限、配额、计费和多租户隔离。
- 复杂前端框架、实时 WebSocket、多语言界面和 PDF 排版导出。
- 自动生成法律结论；许可证部分只做工程风险提示，疑难情况必须人工确认。
- 将模型判断包装成确定事实，或在没有真实评测数据时写简历指标。

## 8. 最终验收场景

最终至少使用以下场景完成现场验收：

1. **活跃且工程完整的仓库**：输出较高维护/工程评分，并展示测试、CI、近期提交等证据。
2. **已归档仓库**：明确识别归档硬风险，不因高 Star 数给出“推荐”。
3. **无明确许可证仓库**：提示二次开发风险并要求人工确认，不给出法律保证。
4. **空或低活跃仓库**：缺失数据不导致崩溃，报告说明证据不足。
5. **无模型 Key**：仍可完成采集、规则评分和报告导出。
6. **GitHub 限流或单工具失败**：任务显示可理解的降级/重试信息，其余章节继续生成。
7. **伪造或缺失证据**：校验器阻止高风险判断进入已验证报告。

完成上述十个功能批次及最终验收后，RepoLens Agent 才达到 `FINAL_GOAL.md` 所定义的可替换简历中普通课程项目的交付标准。
